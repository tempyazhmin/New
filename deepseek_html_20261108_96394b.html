Зафиксированные решения: создаётся нативное Android-приложение; нативный вывод строится на Oboe C++ с декодированием и DSP на Rust; функционал исходного документа не сокращается; поддерживаются Store- и Direct-сборки; первый пользовательский стенд — телефон и Bluetooth; JDK, Android SDK и Rust при реализации размещаются локально внутри проекта.
Полный объём ≠ одновременная неуправляемая разработка. Все функции остаются в продуктовом плане, но внедряются через проверяемые этапы. Переход дальше разрешён после прохождения критериев предыдущего этапа. USB/DSD считаются реализованными только после аппаратной приёмки, а не после появления переключателя в UI.

1. Видение и принципы

Продукт: быстрый локальный Android-плеер с собственным аудиотрактом, серьёзным DSP, удобной библиотекой, честной диагностикой вывода и расширяемой платформой.

Ориентиры по возможностям, а не по копированию UI: Poweramp — звук и настройки выхода; USB Audio Player PRO — работа с ЦАП; Neutron — организация метаданных; Symfonium — профили и перенос настроек; Musicolet — очередь и офлайн-удобства; foobar2000 — ReplayGain и многозначные теги.

  • Local-first: локальная библиотека и воспроизведение не зависят от сети и аккаунтов.
  • Один источник истины: очередь, теги, настройки и состояние вывода не дублируются независимыми автоматами.
  • Честная диагностика: приложение не называет тракт bit-perfect только потому, что пользователь включил опцию.
  • RT-дисциплина: аудиоколбэк не выполняет I/O, JNI, блокировки и работу с кучей.
  • Никаких скрытых изменений: онлайн-теги, DSP fallback и запись в исходные файлы требуют понятного поведения и подтверждения.
  • Измерения вместо обещаний: скорость, энергопотребление, SIMD и качество тракта подтверждаются тестами.

3. Пользовательский опыт

3.1 Основные экраны

  • Библиотека: треки, альбомы, исполнители, album artists, жанры, папки, недавно добавленные.
  • Сейчас играет: обложка, управление, очередь, текст, техническая информация и избранное.
  • Очередь: Play Next, Add to Queue, изменение порядка, удаление, очистка, возврат к исходному порядку shuffle.
  • Эквалайзер: полосы, preamp, АЧХ, пресеты, AutoEQ и профиль текущего устройства.
  • Аудиотракт: источник → декодер → DSP/SRC → фактический Oboe stream → маршрут → состояние Direct/fallback.
  • Плейлисты и история: обложки, импорт/экспорт, частые и недавние прослушивания.
  • Настройки: библиотека, звук, устройства, сеть и приватность, оформление, плагины, backup.

3.2 Функции, позаимствованные у аналогов

Включаются в продукт

  • Отдельные EQ/AutoEQ/preamp для динамика, проводного выхода, Bluetooth и конкретного USB-ЦАП.
  • Multi-select, сортировки, поиск внутри списка, таймер сна по времени и по числу треков.
  • Редактор тегов одного трека и пакетный редактор с preview.
  • Вычисление ReplayGain для файлов без тегов, результат хранится в БД; запись в файл — отдельное действие.
  • M3U8 и версионированный JSON-backup настроек, EQ, плейлистов, избранного и истории.
  • Несколько исполнителей/жанров, composer, sort name и MusicBrainz IDs.

Не блокируют основную версию

  • Несколько независимых именованных очередей.
  • Chromecast, UPnP renderer, Wear OS UI и виджеты рабочего стола.
  • Waveform, визуализаторы, crossfeed/reverb/tempo/pitch.
  • Облачная синхронизация между устройствами.

Это кандидаты после выполнения исходного полного объёма, а не скрытое расширение текущего проекта.

3.3 Доступность и приватность

  • Material 3, тёмная и светлая темы, динамические цвета как опция, контраст и TalkBack.
  • Масштаб шрифта до 200%, уменьшение анимации, доступные actions без жестов-дублёров.
  • Телеметрия выключена по умолчанию; отдельный режим «без сети» блокирует все сетевые обогащения.
  • Онлайн-запросы не отправляют всю библиотеку; каждый провайдер имеет понятную политику кэша.

Почему не «чистый Rust + Oboe»: Oboe — C++-библиотека. Поэтому C++ является осознанной частью native-архитектуры. Kotlin вызывает C++ через JNI; C++ вызывает Rust только через стабильный C ABI. Rust не знает о JNI и Android UI.
  • Версии JDK, AGP, Kotlin, Compose, NDK, Rust и крейтов фиксируются lock-файлами и version catalog.
  • Локальные toolchain-каталоги не попадают в дистрибутив и системные настройки пользователя.
  • Media3 ExoPlayer не декодирует музыку. AMediaCodec разрешён как отдельный decoder backend, а не как замена архитектуре плеера.

7. Состояние, очередь и навигация

QueueManager в Kotlin — единственный владелец музыкальной очереди. Media3 является адаптером для контроллеров; Rust получает только current/next source и не принимает решения о shuffle, repeat или следующем элементе бизнес-очереди.
UI / Bluetooth / Auto / Assistant │ commands ▼ MediaLibrarySession + SimpleBasePlayer adapter │ ▼ PlaybackController │ ├──► QueueManager ──► Room (queue + original order + seed) │ ├──► AudioEngine ───► JNI/C++ ──► Rust current/next │ └──► OutputProfiles / Settings

7.1 Правила очереди

  • Очередь хранит стабильные queueItemId и trackId, а не только позиции в списке.
  • Shuffle имеет область ALL / FOLDER / ALBUM / PLAYLIST / CUSTOM_QUEUE; исходный порядок и seed сохраняются.
  • Repeat: OFF / ONE / QUEUE. Переход рассчитывается один раз в Kotlin.
  • При shuffle без повторов каждый элемент звучит один раз до нового цикла; новые элементы добавляются по детерминированному правилу.
  • Очередь и currentIndex записываются транзакционно. Position checkpoint обновляется каждые 5–10 секунд и на pause/stop/track change/background.
  • После смерти процесса очередь восстанавливается без неожиданного автозапуска звука.

7.2 UI state

  • MVI/UDF: устойчивое состояние — StateFlow<UiState>, one-off события — Channel<UiEffect>.
  • Позиция и FFT не входят в общий UiState. Текстовое время обновляется с низкой частотой, плавный seekbar — в фазе отрисовки.
  • Типобезопасные маршруты Navigation Compose и SavedStateHandle используются для восстановления экрана.
  • Асинхронные методы SimpleBasePlayer завершаются только после отражения команды в Player state; события native engine вызывают invalidateState().

8.4 FTS4 и backup

  • FTS4 external content синхронизируется Room-триггерами; записи выполняются в content table.
  • Индекс содержит нормализованные title/album/artists/genres. Тесты обязаны покрывать кириллицу, регистр, «ё/е», prefix и специальные символы.
  • Миграции тестируются на реальных предыдущих схемах; при миграции внешнего FTS проверяется rebuild индекса.
  • JSON-backup имеет schemaVersion, checksum и сухой прогон валидации. Restore выполняется транзакционно, секреты не экспортируются.
  • M3U8 поддерживает UTF-8, относительные пути и отчёт о ненайденных треках.

9. Библиотека и сканирование

9.1 Разрешения и корни

  • Android 13+: READ_MEDIA_AUDIO для чужих аудиофайлов в MediaStore.
  • Android 10–12: READ_EXTERNAL_STORAGE; собственные файлы приложения читаются без общего разрешения.
  • Первый корень — Music/ через RELATIVE_PATH. Дополнительные корни и гарантированный доступ к дереву — SAF ACTION_OPEN_DOCUMENT_TREE с persistable permission.
  • «Все устройство» означает весь доступный MediaStore.Audio, а не обход Scoped Storage и не скрытые системные каталоги.

9.2 Поведение

  1. При первом запуске объясняется доступ, затем сканируется /Music. До разрешения приложение остаётся работоспособным и позволяет выбрать SAF-папку.
  2. При следующих запусках выполняется быстрая проверка MediaStore version/generation и инкрементальная синхронизация. Полный обход SAF при каждом входе запрещён.
  3. Пользователь может запустить, отменить или повторить сканирование каждого корня, а также полное перечитывание тегов.
  4. SAF traversal использует DocumentsContract и пакетные запросы; DocumentFile.listFiles() не применяется в горячем цикле.
  5. Дифф: (uri, size, mtime, generation где доступно). Ручной full rescan нужен для редких случаев изменения содержимого без надёжной смены признаков.
  6. Обложки не извлекаются массово во время первого прохода. Сначала создаётся лёгкая библиотека, artwork загружается ограниченным пулом и кэшируется.

9.3 FD и жизненный цикл

Два безопасных паттерна:
  • Для декодирования Kotlin вызывает detachFd(); владение передаётся native и заканчивается одним close.
  • Для короткого чтения тегов предпочтителен dup: Rust/C++ владеет дубликатом, Kotlin закрывает исходный PFD через .use. Альтернатива — строго заимствованный FD без закрытия в Rust.
Нельзя передавать один и тот же int в два независимых владельца: fdsan превращает double-close/close-after-reuse в SIGABRT.
  • ContentObserver и MediaStore generation запускают coalesced sync, а не параллельные полные сканирования.
  • WorkManager применяется для длительных задач по выбранным ограничениям; активное ручное сканирование имеет видимый прогресс и cancellation.
  • Потеря SAF permission, unmount SD/USB и исчезновение файла не считаются удалением из библиотеки.

10.2 Границы ABI и владение

  • Через C ABI передаются только POD, дескрипторы и буферы с документированным временем жизни; C++ exceptions и Rust panics не пересекают границу.
  • C++ владеет Oboe stream. Rust не вызывает Oboe API и не закрывает его stream.
  • Rust владеет декодерами и DSP state. Коэффициенты публикуются через triple buffer, тяжёлые объекты освобождаются через control-side reclamation.
  • Очереди событий имеют фиксированную ёмкость; позиция и metering coalesce, критические ошибки сохраняются отдельно.
  • Каждый load/release идемпотентен либо возвращает явную ошибку состояния. Повторный release не должен падать.

Запасные декодеры не добавляются «на всякий случай». Каждый backend должен иметь владельца, тестовый corpus и причину существования. Некорректный файл возвращает ограниченную по размеру ошибку без panic, бесконечного цикла и исчерпания памяти.
  • Lossy-файл нельзя назвать побитово идентичным исходной записи. Direct/bit-perfect относится к неизменной доставке PCM-результата декодера после установленного правила trim.
  • Для streamed/non-seekable источников существует отдельный Source contract; локальный seekable FD и сетевой pipe не имитируют друг друга.
  • Fuzzing и limits обязательны для demuxer, CUE, тегов, SDUI и сетевых ответов.

12. Gapless, seek и SRC

12.1 Переходы

  • Следующий источник открывается заранее по команде Kotlin setNextTrack.
  • Decoder B готовит headers, первый пакет, delay/padding, ReplayGain и output format до окончания Decoder A.
  • Переход выполняется на границе PCM frame; никакой таймер «длительность минус секунда» не используется.
  • MP3/AAC/ALAC trim применяется только при достоверных metadata. Ошибочные значения ограничиваются длительностью потока.
  • При ручном next/previous предзагруженный источник используется только если queueItemId совпадает.

12.2 Изменение формата

СитуацияDSP / SharedDirect PCM
Одинаковые rate/channels/formatGapless через общий outputGapless без DSP, если тракт остаётся Direct
Разные sample ratesSRC к стабильному output rate либо согласованный reopenReopen; бесшовность не гарантируется. SRC запрещён
Разные channel masks / bit depthКонвертация в DSP chainТолько поддерживаемое lossless представление, иначе reopen/fallback с индикацией

12.3 Seek и ресемплер

  • Seek использует time↔frame mapping декодера, затем декодирует от ближайшего подходящего пакета/keyframes и отбрасывает лишнее.
  • После seek flush декодера, SRC и lookahead буферов выполняется по явной команде; старый звук не попадает в новый участок.
  • Rubato работает вне RT callback. Качество задаётся профилем; benchmark и listening/golden tests обязательны.
  • Переходы 44.1↔48 семейств не предполагают, что «кратная частота» автоматически решает качество или совместимость.

13. DSP и real-time

DSP существует только в обычном/DSP режиме. В Direct PCM весь chain обходится, включая цифровую громкость, fades, ReplayGain, EQ, limiter, SRC и dither.

13.1 Порядок обработки

  1. Input gain и de-click ramp при обычном старте/изменении режима.
  2. ReplayGain + пользовательский preamp.
  3. Объединённый банк AutoEQ/PEQ biquad, если профили выражены одним набором фильтров.
  4. Дополнительные встроенные эффекты — только после отдельного включения.
  5. Master volume ramp.
  6. Lookahead limiter с заранее выделенными буферами и metering.
  7. TPDF dither только при реальном понижении разрядности; не при записи float в shared mixer.

13.2 RT-правила

  • DspChain и состояния z1/z2 принадлежат только RT-потоку.
  • Control рассчитывает новые коэффициенты, не пересоздавая состояние фильтров.
  • Коэффициенты интерполируются 64–128 frames; при смене структуры chain используется заранее подготовленный безопасный переход.
  • Все ring/lookahead/convolution буферы имеют верхнюю границу и выделяются заранее.
  • NEON включается после correctness tests; SIMD и scalar выводы сравниваются в допустимом numeric tolerance.
  • Обещания «3–4× от NEON» и «10–15× меньше пробуждений» не являются требованиями: фиксируются только результаты benchmark.

13.3 Защита от перегрузки

  • UI показывает preamp, расчётный peak, gain reduction limiter и счётчик вероятного клиппинга.
  • Auto-preamp может предлагать отрицательный headroom, но не менять пользовательскую настройку скрытно.
  • True-peak limiting является отдельным дорогим профилем, а не бесплатным следствием обычного sample peak limiter.
  • При underrun выход заполняется корректной тишиной/безопасным переходом, счётчик увеличивается, RT не ждёт decoder.

14. ReplayGain

  • Явный пользовательский Track/Album не подменяется автоматически. Правила деградации относятся только к Auto.

  • Album gain сохраняет относительную громкость дорожек альбома; Auto не обещает одинаковую громкость произвольных треков.
  • Scanner работает фоновыми ограниченными задачами, сохраняет результат в БД и не меняет исходный файл без отдельной команды.
  • ReplayGain несовместим с Direct PCM и потому отображается как неактивный, а не как включённый.

16. Direct PCM и bit-perfect

Никакого универсального обещания для встроенного ЦАП. Android 14 документирует AudioMixerAttributes и MIXER_BEHAVIOR_BIT_PERFECT в контексте Lossless USB audio. Exclusive mode Oboe/AAudio сам по себе не означает bit-perfect.

16.1 Последовательность на Android 14+ USB

  1. Отследить AudioDeviceInfo и route changes. Для Bluetooth Direct не предлагать.
  2. Получить getSupportedMixerAttributes(device) и выбрать реально поддерживаемые format/rate/channel mask.
  3. Построить AudioMixerAttributes с MIXER_BEHAVIOR_BIT_PERFECT.
  4. Вызвать setPreferredMixerAttributes(attributes, device, mixerAttributes), проверить результат и зарегистрировать listener изменений.
  5. Открыть Oboe на конкретный device ID с подходящими параметрами; применять Exclusive только когда это поддерживается и оправдано.
  6. Считать фактические rate/format/channels/sharing/performance/buffer. Расхождение — диагностическое состояние, а не успех.
  7. Обеспечить PCM passthrough без DSP и volume. При route/format change выполнить контролируемый reopen.
  8. На release/смену конфигурации очистить preferred mixer attributes и освободить exclusive stream.

16.2 Android 10–13 и встроенные выходы

  • На Android 10–13 стандартный Android USB path не получает маркетинговую гарантию bit-perfect. Подтверждённый обходной путь — собственный UAC2 из раздела 17.
  • Для встроенного ЦАП допускается экспериментальный Direct только при наличии реальных поддерживаемых API и успешной аппаратной проверки.
  • Fallback в Normal/DSP происходит по выбранной пользователем политике: «всегда», «спросить» или «остановить».
  • Тост не является достаточной диагностикой: причина сохраняется в OutputDiagnostics и журнале без личных данных.

16.3 Проверка

  • System API проверяет запрошенную конфигурацию, но не заменяет независимый анализ сигнала.
  • Где возможно используются bit-exact loopback/capture и golden PCM; индикатор частоты на ЦАП сам по себе недостаточен.
  • Изменение системной громкости, эффектов, маршрута или mixer listener немедленно пересматривает статус.
  • Hot-unplug закрывает disconnected stream вне error callback, ставит воспроизведение на паузу по политике и не переносит статус на новый route.

17. DSD, DoP и собственный UAC2

17.1 Три разных пути

ПутьЧто происходитОграничения
DSD→PCMDSD декодируется и фильтруется в PCMНе bit-perfect DSD; DSP разрешён; нужен качественный low-pass и уровень.
DoPDSD биты упаковываются с marker bytes в PCM-фреймыPCM path не должен менять сэмплы; только ЦАП с DoP; опасен вывод как обычного PCM.
Native DSDRaw DSD передаётся непосредственно compatible ЦАПСобственный USB driver и аппаратная поддержка.

При неизменных DoP-фреймах DSD payload остаётся неизменным. Поэтому DoP не описывается как «не bit-perfect по определению»; правильная индикация — DSD over PCM с отдельным результатом проверки тракта.

17.2 Безопасность

  • DoP запрещён до подтверждения поддержки ЦАП; при сомнении используется DSD→PCM или отказ.
  • Переход PCM↔DoP↔Native выполняется с безопасным mute/reopen; старые marker bytes не попадают в новый поток случайно.
  • DSF/DFF reader ограничивает размеры metadata/chunks и не допускает integer overflow при расчёте длительности.

17.3 Собственный UAC2

  • Отдельный компонент после стабилизации PCM/DSP: USB permission, descriptors, alternate settings, isochronous transfers.
  • Adaptive/asynchronous clocking и feedback endpoint тестируются на конкретных чипах; нельзя предполагать один универсальный тайминг.
  • Hot-unplug, нехватка питания, отказ другого Android USB driver, suspend/resume и повторное подключение входят в тесты.
  • Аппаратная громкость использует доступные USB controls и имеет защиту от неожиданного максимума.
  • До появления тестового ЦАП задача имеет статус «реализация без аппаратной приёмки», а не «готово».

18. Сервис, Bluetooth и Android Auto

PlaybackService наследует MediaLibraryService и создаёт MediaLibrarySession. SimpleBasePlayer связывает системные команды с PlaybackController и внешним Oboe/Rust engine.

18.1 Жизненный цикл

  • Foreground service type mediaPlayback, соответствующие permissions и обе service intent-filter для Media3/platform compatibility.
  • Default media notification provider и системные media controls; хрупкие кастомные RemoteViews не используются.
  • CommandButtons для избранного/shuffle и media button preferences — разные API и настраиваются отдельно.
  • ACTION_AUDIO_BECOMING_NOISY и route callbacks: пауза при небезопасном переходе на динамик.
  • AudioFocus с delayed gain; Normal использует плавный duck, Direct по умолчанию ставится на паузу.
  • Очередь и позиция сохраняются; kill системы не создаёт неожиданное «зомби-воспроизведение».

18.2 Bluetooth

  • AVRCP metadata, play/pause/next/previous/seek там, где контроллер поддерживает команды.
  • Bluetooth profile — отдельный OutputDeviceProfile с собственным EQ/AutoEQ.
  • При смене Bluetooth-устройства выбирается его профиль по стабильному device key без раскрытия лишних идентификаторов в UI.
  • Bit-perfect не заявляется: ОС кодирует поток Bluetooth codec. Недоступные OEM codec details не выдумываются.
  • Тесты: reconnect, входящий звонок/duck, задержка metadata, отключение во время gapless, две пары наушников.

18.3 Android Auto и другие контроллеры

  • Дерево: Queue, Recent, Playlists, Albums, Artists, Genres, Folders и Search.
  • Реализуются onGetLibraryRoot, onGetChildren, onGetItem, onSearch, onGetSearchResult с pagination.
  • Результаты не загружают списком 10 000 элементов; artwork и metadata ограничиваются требованиями Auto.
  • Стандартный MediaSession покрывает базовые Wear OS/controller команды; отдельное Wear-приложение не входит в обязательный объём.

19. Плагины и скины

19.1 Разделение возможностей

APK-плагины

  • Streaming/cloud, WebDAV, Subsonic, Jellyfin и другие источники.
  • Метаданные, тексты, обложки и идентификаторы.
  • Декларативные каталоги через SDUI.
  • Скины как resources + JSON tokens.

Только доверенное ядро

  • DSP, декодеры, SRC, limiter и RT-визуализация.
  • Oboe callback и владение native buffers.
  • Очередь, backup и управление разрешениями.

Binder не используется на каждый аудиобуфер. Источник передаётся как authenticated URL/request description либо FD/pipe с backpressure, явным закрытием и cancellation.

19.2 Discovery и доверие

  1. PackageManager.queryIntentServices по публичному action; необходимые <queries> объявлены для Android 11+.
  2. Проверяются package, exported component, SDK major/minor, capabilities и signature hash.
  3. При первом включении пользователь видит разработчика, запрошенные capabilities и источник установки.
  4. Смена подписи/major SDK отключает плагин до повторного подтверждения.
  5. Bind имеет timeout, DeathRecipient, ограничение размеров ответов и защиту от бесконечных стримов.
  6. Плагин выполняется в процессе своего APK/UID, но это не отменяет валидацию его данных.

19.3 SDUI

  • Белый список компонентов: sections, lists, cards, text, images, search, toggles и ограниченные navigation actions.
  • Никаких arbitrary Compose, DEX, reflection, JavaScript, arbitrary intents и неограниченных URI.
  • Размер schema, глубина вложенности, число элементов и строки ограничены; рендер устойчив к malformed input.
  • Статический route содержит pluginPackage/path; динамический код в процесс плеера не загружается.

19.4 Скины

  • Только цвета, размеры, радиусы, typography scale и разрешённые resources.
  • Токены валидируются по schema; небезопасные contrast/size не ломают доступность без предупреждения.
  • CompositionLocalProvider применяет тему реактивно; сбой скина возвращает встроенную тему.
  • Скин не меняет аудиологику и не получает сетевых/файловых capabilities автоматически.

20.2 Сетевые правила

  • Обязательные User-Agent/contact, rate limit, timeout, retry с jitter и exponential backoff.
  • 429/5xx не запускают шторм запросов; кэшируются negative results на ограниченное время.
  • Размер ответа, глубина JSON/XML, изображения и redirect ограничены. TLS не отключается.
  • Пакетное обогащение — только по включённой опции; charging/unmetered/battery constraints настраиваются.
  • При старте воспроизведения тяжёлая фоновая работа приостанавливается по ресурсной политике, а не потому что для AcoustID нужен микрофон.
  • Секреты хранятся в механизме защищённого хранения, не в Room backup, SDUI или логах.

20.3 Редактор тегов

  • Сначала read-only preview: старое/новое значение, источник и список затронутых файлов.
  • Запись в MediaStore требует соответствующего write consent; SAF write permission проверяется отдельно.
  • Ошибка части пакета не выдаётся за полный успех; создаётся отчёт и возможность повторить failed items.
  • После записи обновляются Room/FTS и artwork cache без удаления истории.

21.2 Основные оптимизации

  • Oboe PowerSaving для обычного music playback, если фактический stream его поддерживает; Direct/Exclusive настраивается отдельно.
  • Буферы подбираются по underrun/latency/power измерениям, а не фиксированные 40–80 мс для всех устройств.
  • Программное декодирование может потреблять больше энергии аппаратного. MediaCodec/offload рассматриваются по результатам замера без нарушения DSP/Direct семантики.
  • Artwork downsample, bounded memory/disk cache, paging списков и никаких полных Bitmap в модели списка.
  • 60 Hz position не записывается в БД/DataStore и не рекомпонует весь экран.
  • Release build, R8/ProGuard и native symbols проверяются отдельно; debug benchmark не считается результатом.

22. Надёжность и безопасность

22.1 Ошибки и восстановление

  • Единый taxonomy: permission, missing file, unsupported codec, corrupt data, network, route, disconnected, underrun, internal.
  • Ошибка одного трека не роняет service и не создаёт бесконечный autoplay-next loop; есть лимит последовательных ошибок.
  • Native panic/exception перехватывается на FFI boundary; crash не маскируется ложным «unsupported format».
  • Room migrations и backup restore имеют rollback; corrupted DataStore имеет documented recovery.
  • Disconnect Oboe обрабатывается control thread; никакого close из error callback с последующим deadlock.
  • Приложение корректно работает при отказе в разрешениях, отключённой сети, restricted battery и process death.

22.2 Безопасность

  • Все внешние файлы, теги, CUE, изображения, SDUI и AIDL payloads считаются недоверенными.
  • Нет arbitrary path из plugin/network: используются разрешённые URI/FD и capability checks.
  • PendingIntent/Intent flags и exported components проходят явный security review.
  • Логи не содержат URL credentials, tokens, полные пользовательские пути по умолчанию и содержимое текстов песен.
  • Release включает dependency/license inventory: Rust MPL/MIT/Apache, Oboe, Media3, libopus и остальные компоненты.
  • Никакого скрытого кода для обхода политики Store, разрешений Android или защиты сервисов.

25. Definition of Done

  • Все требования раздела 2 имеют реализацию, тест и статус: принято / заблокировано конкретным оборудованием / отклонено согласованным изменением.
  • Store- и Direct-сборки собираются из чистого checkout с локальными toolchains и закреплёнными версиями.
  • Локальная библиотека на 10k треков, поиск, плейлисты, очередь и process death проходят приёмку.
  • Все заявленные форматы имеют тестовый corpus; gapless ограничения задокументированы и видны.
  • RT callback не содержит запрещённых операций; soak tests не выявляют утечек и неприемлемых xruns.
  • Bluetooth/Auto/AudioFocus/noisy проверены на реальном телефоне.
  • UI не приписывает bit-perfect Bluetooth или неподтверждённому встроенному/USB тракту.
  • USB/DSD отмечены готовыми только для фактически проверенных устройств.
  • Backup/restore, M3U8 и миграции не приводят к потере данных.
  • Плагины не исполняют чужой код в процессе плеера, а capabilities и updates контролируются пользователем.
  • Доступность, приватность, лицензии, подпись и обновления проверены для обоих каналов.
